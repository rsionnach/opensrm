# Contributing to Service Reliability Manifest

Thank you for your interest in contributing to the Service Reliability Manifest specification!

## Ways to Contribute

### Report Issues
- Found a bug in the spec? Open an issue
- Have a question? Start a discussion
- See something unclear? Let us know

### Suggest Improvements
- Propose new features or fields
- Suggest clarifications to existing documentation
- Share real-world use cases that could inform the spec

### Submit Changes
- Fix typos or improve documentation
- Add examples
- Propose spec changes (see RFC process below)

## Getting Started

1. **Fork the repository** and clone it locally
2. **Create a branch** for your changes
3. **Make your changes** following the guidelines below
4. **Submit a pull request**

## Guidelines

### Documentation Changes
- Use clear, concise language
- Follow existing formatting conventions
- Include examples where helpful

### Example Manifests
- Place examples in the `examples/` directory
- Name files descriptively: `<service-type>.reliability.yaml`
- Include comments explaining key decisions
- Ensure examples validate against the JSON Schema

### Specification Changes

For changes to the specification itself:

1. **Minor clarifications** can be submitted directly as PRs
2. **Significant changes** require an RFC (see [GOVERNANCE.md](GOVERNANCE.md))

When proposing spec changes:
- Explain the problem being solved
- Show example usage
- Consider backward compatibility
- Update the JSON Schema if needed

## Pull Request Process

1. Ensure your changes pass validation
2. Update documentation as needed
3. Add or update examples if relevant
4. Reference any related issues

## Code of Conduct

This project follows a standard open source code of conduct. Please be respectful and constructive in all interactions.

## Questions?

Open a GitHub issue or start a discussion. We're happy to help!
