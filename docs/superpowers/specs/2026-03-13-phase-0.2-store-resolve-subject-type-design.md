# Phase 0.2: Store-level resolve() + Subject Type Fix

## Summary

Two small changes to the verdict library that eliminate a common footgun and unblock Mayday's Communication agent.

1. **Store-level `resolve()`**: A concrete method on `VerdictStore` ABC that combines `get()` → `core.resolve()` → `update_outcome()` into a single call. Eliminates the two-step pattern where callers must remember to persist after resolving.

2. **Subject type addition**: Add `"communication"` to `VALID_SUBJECT_TYPES` so Mayday's Communication agent can emit verdicts without using `"custom"` as a workaround.

## Motivation

### Store-level resolve()

The current pattern for resolving a stored verdict requires two steps:

```python
from verdict.core import resolve
resolve(verdict, status="confirmed")           # mutates in-memory object
store.update_outcome(verdict.id, verdict.outcome)  # persists to store
```

For `MemoryStore`, forgetting step 2 still works because the store holds a reference to the same object. For `SQLiteVerdictStore`, forgetting step 2 silently loses the resolution — the stored copy remains `pending`. This was the root cause of 8 test failures during Phase 0.1 parameterization.

The fix: `store.resolve(verdict_id, status="confirmed")` does both steps in one call.

### Subject type

`VALID_SUBJECT_TYPES` currently has 10 types. Mayday's Communication agent needs `"communication"` for its verdict `subject.type`. The implementation plan (Critical Issue #2) specifies adding this type.

## Design

### Store-level `resolve()` — concrete method on VerdictStore ABC

**File:** `verdicts/lib/python/verdict/store.py`

**Signature:**

```python
def resolve(
    self,
    verdict_id: str,
    status: str,
    override: dict | Override | None = None,
    ground_truth: dict | GroundTruth | None = None,
    resolution: str | None = None,
) -> Verdict:
```

**Behavior:**

1. `verdict = self.get(verdict_id)` — raises `KeyError` if `None`
2. `core.resolve(verdict, status, override, ground_truth, resolution)` — validates pending check, valid statuses, coerces override/ground_truth dicts
3. `updated = self.update_outcome(verdict_id, verdict.outcome)` — persists to store
4. Returns `updated` (the persisted version from `update_outcome()`, which is the authoritative copy)

**Key decisions:**

- **Concrete, not abstract**: Implemented once on `VerdictStore`. Both `MemoryStore` and `SQLiteVerdictStore` inherit it. No store-specific override needed.
- **Delegates to `core.resolve()`**: All validation rules (pending check, valid statuses, override/ground_truth coercion, `closed_at` timestamping) stay in one place. No duplication.
- **ID-based, not object-based**: Takes `verdict_id: str`, not `verdict: Verdict`. The stored copy is authoritative. Callers don't need the in-memory object.
- **Same error semantics**: `KeyError` for missing verdict (from `get()`), `ValueError` for already-resolved or invalid status (from `core.resolve()`).
- **Not concurrency-safe for same verdict**: Two concurrent `store.resolve()` calls on the same verdict ID could both pass the pending check. This is a pre-existing limitation (the two-step pattern has the same race). True atomicity would require `UPDATE ... WHERE outcome_status = 'pending'` with row-count check — deferred to a future phase if concurrent resolution becomes a real concern.

**Import addition:** `store.py` will import `core.resolve as _core_resolve` (aliased to avoid shadowing the new method name).

### Subject type addition

**File:** `verdicts/lib/python/verdict/models.py`

Add `"communication"` to the `VALID_SUBJECT_TYPES` frozenset. One-line change.

Updated set (11 types):
```python
VALID_SUBJECT_TYPES = frozenset({
    "agent_output", "correlation", "triage", "investigation",
    "remediation", "review", "classification", "recommendation",
    "moderation", "communication", "custom",
})
```

### Public API

No changes needed to `__init__.py`. `resolve` is already exported from `core`. The store-level `resolve()` is accessed as `store.resolve(...)` — it's a method, not a standalone function.

## Tests

All new tests parameterized against both `MemoryStore` and `SQLiteVerdictStore` via the existing `store` fixture.

**File:** `verdicts/lib/python/tests/test_store.py`

New test class `TestStoreResolve`:

| Test | Description |
|------|-------------|
| `test_resolve_confirmed` | Create verdict, `store.resolve(v.id, "confirmed")`, verify `store.get(v.id).outcome.status == "confirmed"` and `closed_at` is set |
| `test_resolve_with_override` | Resolve with `override={"by": "human", "reasoning": "wrong"}`, verify override fields persisted |
| `test_resolve_with_ground_truth` | Resolve with `ground_truth={"signal": "test_failure"}`, verify ground_truth persisted |
| `test_resolve_with_resolution` | Resolve with `resolution="All good"`, verify resolution string persisted |
| `test_resolve_missing_raises` | `store.resolve("vrd-nonexistent", "confirmed")` raises `KeyError` |
| `test_resolve_already_resolved_raises` | Resolve twice raises `ValueError` on second call |
| `test_resolve_invalid_status_raises` | `store.resolve(v.id, "bogus")` raises `ValueError` |

New test in existing `TestStorePutAndGet` or standalone:

| Test | Description |
|------|-------------|
| `test_communication_subject_type` | `create(subject={"type": "communication", ...})` succeeds, round-trips through store |
