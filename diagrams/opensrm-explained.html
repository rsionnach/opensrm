1 — Manifest Format

The Reliability Manifest

Without OpenSRM, reliability lives in Confluence pages, Slack threads, and people’s heads. The manifest is a single YAML file per service — versioned in Git — that declares exactly what “reliable” means: SLO targets, ownership, dependencies, and contracts.

It uses a Kubernetes-style structure (apiVersion, kind, metadata, spec) that ops teams already understand.

“A manifest is a contract with the future — it says what you promise before you’re under pressure to promise anything.”
examples/api-minimal.yaml — Minimal manifest
apiVersion: opensrm/v1 # MUST: API version kind: ServiceReliabilityManifest # MUST: Document type metadata: name: payment-api tier: critical # critical | high | standard | low spec: type: api # determines applicable SLOs slos: availability: target: 0.9995 # ratio 0-1, NOT percentage window: 30d

How it’s implemented

The manifest format is defined in spec/v1/specification.md (12 chapters). The GitHub Action at action/src/index.ts implements validation using AJV (Another JSON Validator) with the schema imported from ./schema/v1.json. The action uses @actions/glob to discover manifest files and validates each against the schema.

action/src/index.ts — TypeScript manifest interface
interface SRMManifest { apiVersion: string; // "opensrm/v1" kind: string; // "ServiceReliabilityManifest" | "Template" metadata: { name: string; team: string; tier: string; // "critical" | "high" | "standard" | "low" template?: string; // inheritance from Template kind }; spec: { type?: string; // 6 service types contract?: { availability?: number; latency?: object; judgment?: object; }; slos?: { availability?: object; latency?: object; judgment?: object; }; dependencies?: Array<{ service: string; critical?: boolean; expects?: object; }>; instrumentation?: { events: { decision: string; reversal: string; }; }; }; }
Gotchas and traps
  • Ratios, not percentages. 0.999 means 99.9%. Schema enforces 0.0–1.0.
  • Duration format is strict: [0-9]+(ms|s|m|h|d|w). No spaces, no ISO 8601.
  • Six service types — api, worker, stream, ai-gate, batch, database — each with different applicable SLOs.
  • Two kinds: ServiceReliabilityManifest (primary) and Template (reusable defaults for inheritance via metadata.template).
2 — SLO Definitions

Service Level Objectives

SLOs are the heart of a manifest. They answer: “How good does this service need to be, measured how, over what window?” Each service type gets a specific set of applicable SLOs — preventing nonsensical configs like measuring “lag” on an API.

“An SLO without a window is a wish. An SLO without a target is a metric. You need both.”

Standard SLOs (api type)

Availability — ratio of successful responses
Latency — percentile targets (p50/p90/p95/p99/p999)
Error rate — ratio of errors
Throughput — requests per second

Type-Specific SLOs

Worker: processing_time, success_rate
Stream: lag (max_seconds), throughput
Batch: duration, schedule_adherence, data_freshness
Database: query_latency, replication_lag, connection_availability

spec/v1/specification.md — SLO structure patterns
# Every SLO needs target + window availability: target: 0.9995 # ratio 0-1 window: 30d # Latency needs at least one percentile latency: p50: 50ms p99: 200ms # at least one percentile required target: 0.99 # ratio meeting threshold window: 30d # Worker-specific: processing time processing_time: p99: 5m # 99% of jobs in 5 minutes target: 0.99 window: 7d # Stream-specific: consumer lag lag: max_seconds: 30 target: 0.99 window: 7d

How it’s implemented

Each SLO type has its own JSON Schema definition in spec/v1/schema.json: AvailabilitySLO, LatencySLO, ErrorRateSLO, ThroughputSLO, ProcessingTimeSLO, LagSLO, SuccessRateSLO, DurationSLO, ScheduleAdherenceSLO, DataFreshnessSLO, QueryLatencySLO, ReplicationLagSLO, ConnectionAvailabilitySLO. The schema uses additionalProperties: false to reject unknown fields and validates Duration via regex pattern ^[0-9]+(ms|s|m|h|d|w)$.

Gotchas and traps
  • Latency SLOs need at least one percentile plus a target ratio.
  • Window defaults vary: 30d for API/database, 7d for worker/stream.
  • success_criteria on availability is optional — defaults to 2xx + 3xx status codes.
3 — Contracts & Dependencies

External Promises vs Internal Targets

The manifest separates what you guarantee to others (contract) from what you aim for internally (SLOs). Internal targets are always tighter. Dependencies declare what you need from upstream services via the expects field — enabling tooling to validate feasibility at CI time.

“Contracts are what you advertise. SLOs are how you sleep at night.”
examples/api-full.yaml — Contract vs SLO + dependencies
spec: contract: # what you PROMISE dependents availability: 0.9995 latency: p99: 300ms # external: 300ms throughput: max_rps: 5000 slos: # internal targets (TIGHTER) latency: p99: 200ms # internal: 200ms (100ms headroom) target: 0.99 dependencies: - service: user-service critical: true # failure = our failure manifest: https://github.com/.../service.reliability.yaml expects: # what we NEED from them availability: 0.999 latency: p99: 100ms - service: stripe-api type: external critical: true expects: availability: 0.9999

How it’s implemented — Dependency math

The expects field enables NthLayer to perform feasibility validation. If you promise 99.95% availability but depend critically on a service guaranteeing only 99.9%, the math doesn’t work. The combined availability of N critical serial dependencies is the product of their individual availabilities. NthLayer computes this ceiling and rejects manifests that violate it during nthlayer validate.

Gotchas and traps
  • Contract judgment SLOs use different field names: spec.contract.judgment.max_reversal_rate (not reversal_rate.target).
  • The manifest field on a dependency is optional — it points to the dependency’s own OpenSRM file for cross-referencing.
  • critical: false (default) means the dependency is non-critical — its failure degrades but doesn’t break your service.
4 — JSON Schema

Machine-Readable Validation

Without the schema, manifests are documentation. With it, they’re enforceable. The JSON Schema (spec/v1/schema.json, draft-07) makes every YAML field machine-checkable — CI pipelines, editors, and linters catch errors before they ship.

spec/v1/schema.json — Core type definitions
"Duration": { "type": "string", "pattern": "^[0-9]+(ms|s|m|h|d|w)$" // strict, no ISO 8601 } "Ratio": { "type": "number", "minimum": 0, "maximum": 1 // enforces 0-1 range } "ServiceType": { "enum": ["api", "worker", "stream", "ai-gate", "batch", "database"] } "Tier": { "enum": ["critical", "high", "standard", "low"] }
action/src/index.ts — AJV validation setup
import Ajv from 'ajv'; import addFormats from 'ajv-formats'; import schemaV1 from './schema/v1.json'; // schema embedded in bundle // Schema ID: https://opensrm.io/schemas/v1/manifest.json // Uses oneOf: ServiceReliabilityManifest | Template // additionalProperties: false on all SLO types

How it’s implemented

The GitHub Action (action.yml at repo root, published as rsionnach/opensrm@v1) uses @actions/glob to find *.reliability.yaml files, parses with js-yaml, and validates against the schema via AJV. The schema is bundled into action/dist/index.js at build time. Schema defines 13+ SLO type schemas, contract schemas (with separate ContractLatency, ContractThroughput, ContractJudgment), and dependency schemas with the expects field.

Gotchas and traps
  • Schema is embedded in the Action bundle. When schema changes, the action must be rebuilt (npm run build in action/).
  • Schema ID is https://json.schemastore.org/opensrm.json for editor integration.
5 — AI Gates & Judgment SLOs

Measuring AI Decision Quality

Traditional SLOs measure infrastructure: is it up? Is it fast? But AI-powered services make decisions. These need a fundamentally different quality measurement. The ai-gate type extends API SLOs with judgment SLOs that measure decision quality over time.

An AI gate produces three outputs: approve (commit to allowing), reject (commit to denying), or escalate (decline to decide). Escalation is abstention — it keeps metrics clean.

“A fast, available AI that makes wrong decisions isn’t reliable — it’s confidently wrong at scale.”

Reversal Rate

How often humans override. Measured after observation_period.

target: 0.03

High-Confidence Failure

Confident but wrong. Most dangerous failure mode.

target: 0.01 threshold: 0.9

Calibration (ECE)

Does 80% confidence = 80% accuracy?

target: 0.10

Feedback Latency

How long until outcome is known.

p50: 48h p90: 168h
examples/ai-gate-full.yaml — Full judgment SLOs
spec: type: ai-gate contract: judgment: max_reversal_rate: 0.05 # external promise max_hcf_rate: 0.02 slos: judgment: reversal_rate: target: 0.03 # internal target (tighter) window: 30d observation_period: 24h # wait before counting high_confidence_failure: target: 0.01 confidence_threshold: 0.9 calibration: target: 0.10 # Expected Calibration Error instrumentation: # REQUIRED for ai-gate events: decision: ai_gate.decision reversal: ai_gate.reversal outcome: ai_gate.outcome

How it’s implemented — 4-Level Maturity Model

Defined in spec/v1/judgment-slos.md. Each level builds on the previous:

Level 1 (Reactive): reversal_rate + HCF. Minimal effort — instrument events, set thresholds. Days to implement. Limitation: only measures quality when humans are forced to engage.

Level 2 (Proactive): Add audit sampling (10% random sample reviewed by humans). audit_accuracy is your unbiased signal. If reversal_rate is 3% but audit_accuracy is 85%, you have 12% hidden failures.

Level 3 (Outcome): Defect correlation via downstream signals (incidents, rollbacks, chargebacks). Ground truth. 90-day windows because outcomes are delayed.

Level 4 (Behavioral): Escalation bounds (min/max), segment-level targets, calibration ECE, stability/volatility monitoring. Full governance.

spec/v1/judgment-slos.md — Metric definitions
// Escalations excluded from both numerator and denominator reversal_rate = count(reversals where decision_age < observation_period) / count(decisions where decision ∈ [approve, reject]) hcf_rate = count(reversals where original_confidence >= threshold) / count(decisions where confidence >= threshold) // Buckets partition decisions by confidence (0.0-0.1, 0.1-0.2, ...) ECE = Σ (|bucket_accuracy - bucket_confidence| * bucket_weight)
Gotchas and traps
  • Instrumentation is mandatory for ai-gate. Without event mappings, judgment SLOs can’t be measured.
  • Contract judgment uses different field names: max_reversal_rate (not reversal_rate.target).
  • Escalation is abstention, not a flagged decision. The AI hasn’t decided; a human must. This keeps reversal_rate clean.
  • Level 2 audit is a process, not just a metric. 10% sample at 1000 decisions/day = 100 reviews/day = ~3.3 hours of review work.
6 — NthLayer Compiler

From Declaration to Reality

Without NthLayer, manifests are documentation. With it, they become operational. NthLayer is a deterministic compiler: same manifest in, same artifacts out. No AI, no reasoning — just template expansion and arithmetic.

ARCHITECTURE.md — NthLayer CLI interface
nthlayer validate <manifest> # Schema + dependency math nthlayer generate <manifest> -o <dir> # Generate all artifacts nthlayer check-deploy <manifest> # CI/CD deployment gate nthlayer topology export <manifest> # Export for Sitrep nthlayer verify <manifest> # Verify metrics exist in Prometheus nthlayer portfolio # Org-wide SLO health view

Why it’s not an agent

Validation is schema checking. Generation is template expansion. Dependency math is arithmetic. Deployment gating is threshold comparison. All deterministic. The Reasoning Boundary principle: agent capabilities are reserved for components requiring interpretation of ambiguous inputs. NthLayer does the same thing every time given the same input — it’s a tool. Agents call NthLayer when they need topology data or artifact regeneration.

7 — Sitrep Agent

Pre-Correlated Situation Awareness

“A deployment happened 12 minutes ago to auth-service, and now checkout latency is spiking, and these two services share a critical dependency path.” Connecting those dots requires understanding topology, temporal proximity, and causal plausibility. That’s interpretation, not aggregation — that’s why Sitrep is an agent.

Inputs

Metrics (Prometheus remote write)
Alerts (Alertmanager webhook)
Changes (GitHub, ArgoCD, LaunchDarkly)
Logs (OTLP)
Topology (NthLayer tool call)

Generation Modes

Batch: Every 5 min (normal ops)
Incident: Immediate on webhook
Refresh: Every 1 min during incidents
Manual: On-demand API call

stateDiagram-v2
  [*] --> WATCHING
  WATCHING --> ALERT : elevated signal
  ALERT --> INCIDENT : incident declared
  ALERT --> WATCHING : signal subsides
  INCIDENT --> WATCHING : resolved
  INCIDENT --> DEGRADED : own judgment SLO breach
  DEGRADED --> WATCHING : performance recovers
components/sitrep/ — Hybrid generation model (Go)
type SnapshotGenerator struct { batchInterval time.Duration // 5 minutes incidentRefreshInterval time.Duration // 1 minute activeIncidents map[string]*IncidentContext windowManager *WindowManager correlationEngine *CorrelationEngine logSummarizer *LogSummarizer } type IncidentContext struct { Incident Incident LastRefresh time.Time RefreshTicker *time.Ticker Snapshots []string // IDs of generated snapshots Done chan struct{} }

How it’s implemented

Sitrep is a long-running Go service with a reasoning loop: Observe → Correlate → Assess → Publish. It has 4 states (WATCHING, ALERT, INCIDENT, DEGRADED). In DEGRADED mode, it reduces confidence in correlations and flags for human review. Service identity comes from the OpenSRM manifest catalog — not auto-discovery. Every correlation assessment emits a gen_ai.decision.* OTel event. When a human disagrees, that emits gen_ai.override.*. Sitrep has its own type: ai-gate manifest with judgment SLOs for correlation accuracy.

Gotchas and traps
  • Sitrep is itself an ai-gate. It measures its own correlation accuracy via judgment SLOs. If quality drops, Arbiter puts it in DEGRADED mode.
  • Snapshots are JSON, not dashboards. Designed for both human and LLM consumption.
  • Outputs go to REST API + SSE/WebSocket + ClickHouse storage.
8 — Mayday & Arbiter

Incident Response & Governance

Mayday: 4 specialized agents in a pipeline. Arbiter: the meta-agent that watches all agents’ judgment SLO metrics and adjusts autonomy. One-way safety ratchet: can reduce autonomy without approval, cannot increase without human sign-off.

How it’s implemented — Arbiter governance

The Arbiter watches Prometheus for all agents’ judgment SLO metrics. Its governance actions: reversal rate exceeding target → increase human review threshold. Error budget exhausted → reduce to advisory-only mode. Sustained good performance → propose autonomy increase (requires human approval). Calibration drift → flag for retraining. Multiple agents degrading → escalate to humans for system-wide review. The orchestrator is NOT an agent — it’s a deterministic state machine that sequences execution. The pipeline is fixed; agents reason within their step.

Gotchas and traps
  • Remediation authority is limited: pre-approved safe actions (rollback, scale, feature flag) without approval. Novel fixes require human sign-off.
  • Both Mayday and Arbiter are architecture-only — documented design, not running code.
  • Each Mayday agent has its own judgment SLO. Triage: severity reversal <10%. Investigation: root cause agreement 70%. Communication: human edit rate <15%. Remediation: fix success rate 80%.
9 — OTel Semantic Conventions

The Telemetry That Closes the Loop

Two proposed OTel conventions make the ecosystem measurable: Change Events (change.*) for change-incident correlation, and Decision Telemetry (gen_ai.decision.*, gen_ai.reversal.*) for judgment SLO measurement.

Change Events

change.id — unique identifier
change.type — deployment, configuration, feature_flag, infrastructure, database
change.scope.service — affected service
change.risk.score — 0.0-1.0

Targeting OTel CI/CD SIG

Decision Telemetry

gen_ai.decision.* — decision event with confidence
gen_ai.reversal.* — human override
gen_ai.outcome.* — actual result

Targeting OTel GenAI SIG
Transport: OTel Events

How it closes the loop

Every agent decision emits gen_ai.decision.*. Human overrides emit gen_ai.reversal.*. These flow to Prometheus via OTel Collector. NthLayer generates recording rules for each agent’s judgment SLOs (from their type: ai-gate manifest). The Arbiter reads these metrics and adjusts autonomy. Agents are monitored by the same system they help operate — the loop is closed.
