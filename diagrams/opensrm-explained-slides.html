The Manifest

YAML structure for reliability as code

Abstraction 1

The Reliability Manifest

  • One YAML file per service, versioned in Git
  • Kubernetes-style structure: apiVersion, kind, metadata, spec
  • Declares SLO targets, ownership, dependencies, contracts
  • Moves reliability left — before deployment, not after incidents

Minimal Manifest

api-minimal.yaml 
apiVersion: opensrm/v1
kind: ServiceReliabilityManifest
metadata:
  name: payment-api
  tier: critical           # critical | high | standard | low
spec:
  type: api                  # determines applicable SLOs
  slos:
    availability:
      target: 0.9995         # ratio 0-1, NOT percentage
      window: 30d

SLO Definitions

Reliability targets with teeth

Abstraction 2

Service Level Objectives

  • Every SLO requires a target (ratio 0–1) and a window
  • Service type determines which SLOs apply
  • Latency SLOs require at least one percentile (p50/p90/p95/p99)
  • Prevents nonsensical configs — no “lag” on an API

SLOs by Service Type

TypePrimary SLOsDefault Window
apiavailability, latency, error_rate, throughput30d
workeravailability, processing_time, success_rate7d
streamavailability, lag, throughput7d
ai-gateextends api + judgment SLOs30d
batchavailability, duration, schedule_adherence, data_freshness30d
databaseavailability, query_latency, replication_lag, connection_availability30d
03

Contracts & Dependencies

External promises vs internal targets

Contract

What You Promise

  • spec.contract.availability: 0.9995
  • spec.contract.latency.p99: 300ms
  • External guarantees to dependents
  • Breaking this means breach of trust

Internal SLOs

What You Target

  • spec.slos.availability.target: 0.9998
  • spec.slos.latency.p99: 200ms
  • Tighter than contract — headroom for surprises
  • Alerting triggers on internal, not contract

Dependency-Aware SLOs

api-full.yaml 
dependencies:
  - service: user-service
    critical: true               # failure = our failure
    expects:                     # what we NEED from them
      availability: 0.999
      latency:
        p99: 100ms
  - service: stripe-api
    type: external
    critical: true
    expects:
      availability: 0.9999

Confident but wrong

48h

AI Gate Manifest

ai-gate-full.yaml 
spec:
  type: ai-gate
  slos:
    judgment:
      reversal_rate:
        target: 0.03
        window: 30d
        observation_period: 24h
      high_confidence_failure:
        target: 0.01
        confidence_threshold: 0.9
  instrumentation:             # REQUIRED
    events:
      decision: ai_gate.decision
      reversal: ai_gate.reversal

Design Principle

The Reasoning Boundary

  • Does it need to reason about ambiguous inputs? → Agent
  • Same output every time given same input? → Tool
  • Queryable state? → Data Source
  • NthLayer is a tool — deterministic template expansion

Sitrep Agent

Pre-correlated situation awareness

Why It Exists

Connecting the Dots

  • Correlates metrics, alerts, changes, logs with topology
  • 4 generation modes: batch (5m), incident, refresh (1m), manual
  • Outputs JSON snapshots for human and LLM consumption
  • Is itself an ai-gate with its own judgment SLOs

Governance

Arbiter: One-Way Safety Ratchet

  • Watches Prometheus for all agents’ judgment SLO metrics
  • Can reduce autonomy without approval
  • Cannot increase autonomy without human sign-off
  • Reversal rate high → more human review required

OTel Conventions

The telemetry that closes the loop

Change Events

Operational Changes

  • change.id — unique identifier
  • change.type — deploy, config, feature_flag
  • change.risk.score — 0.0 to 1.0
  • Targeting OTel CI/CD SIG

Decision Telemetry

AI Decision Events

  • gen_ai.decision.* — decision + confidence
  • gen_ai.reversal.* — human override
  • gen_ai.outcome.* — actual result
  • Targeting OTel GenAI SIG
